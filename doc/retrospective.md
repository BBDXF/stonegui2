# stonegui — 项目复盘与收尾

> **状态：2026-09 起停止扩展功能面。**
>
> 项目本身可运行、可交付（31 个 host 标签、主题系统、CJK 输入、热重载都已完成
> 并有回归覆盖）。停止的不是"维护"，而是"继续把它补成一个完整跨平台桌面 GUI
> 框架"这个方向。本文记录瓶颈、根因、以及若要重启该走哪条路。
>
> 前序文档：[`prompts.md`](prompts.md) 是最初的设计愿景（已归档、部分过时），
> [`roadmap.md`](roadmap.md) 是 Phase III 的执行记录（A–E 全部完成）。
> 本文是它们的**终点**，不是新的任务队列。

## 1. 项目实际达成了什么

| 维度 | 结果 |
|---|---|
| 代码量 | 9132 行（C 5131 / JS+d.ts 1203 / 测试与示例 2834） |
| 组件 | 31 个 host 标签，覆盖表单、图表、表格、菜单、日历、虚拟键盘 |

应用框架"这个标尺下才成立。

## 2. 遇到的瓶颈

关键认知：**剩下的缺口不是"功能"，是"子系统"。** 每一条都不是加几个
`js_setProperty` 分支能解决的。

### 2.1 桌面窗口语义缺失

单窗口架构（[`main.c`](../src/main.c) 只创建一个 `lv_sdl_window_create`）。
没有多窗口、独立对话框、原生菜单栏、系统托盘、系统文件选择框、系统通知。
`showMsgbox` 只是应用内的模态层，不是 OS 级窗口。

多窗口在 LVGL 9.x 理论可行（`lv_display_t` 支持多实例），但**原生 chrome
每个平台一套 API**，与 LVGL 无关，得自己写三份。

### 2.2 输入模型与桌面语义不匹配

LVGL 的 indev 抽象是"**指针（触摸）+ 编码器/按键组**"，不是桌面的
"鼠标 + 键盘 + 焦点链"。当前项目里所有桌面交互都是**绕开 LVGL、直接拦截 SDL
事件**补出来的：

| 需求 | 现状 | 位置 |
|---|---|---|
| 滚轮滚动 | LVGL 自带 `lv_sdl_mousewheel_create` 是编码器语义（滚焦点控件而非光标下的控件），弃用，自己按光标命中重写 | `sg_handle_mousewheel` |
| Ctrl+A/C/V/X、Home/End | LVGL 键盘驱动不处理组合键，在 SDL 事件钩子里拦 `SDL_KEYDOWN` + `SDL_GetModState()` | `sdl_event_watch` |
| 多字节输入 | LVGL SDL 键盘驱动逐字节吐出，拆坏 UTF-8，替换 read_cb；且该实现**依赖 LVGL 私有结构体布局**，升级 LVGL 必须重新核对 | `sg_keyboard_read` |

仍然缺失且同样得手搓的：右键上下文菜单、拖放（drag-and-drop 到另一个容器）、
框选多选、真正的 tab-index 顺序控制（现在只是"控件创建顺序"线性入 `g_group`）、
悬停与按下的语义区分。

**这三处 workaround 是先兆，不是终点**——补丁模式的维护成本会随交互丰富度
指数增长。

### 2.3 无障碍完全空白

`lv_conf.h` 里没有任何 accessibility 开关。要支持屏幕阅读器，需要分别对接
Windows UIA、macOS NSAccessibility、Linux AT-SPI 三套完全不同的 API。
**人年级工作量，且换任何框架都绕不开**（Qt/Flutter 也只是做得比零好）。

### 2.4 文本排版能力有限

LVGL 的文本引擎距离 HarfBuzz 级的**字形整形、BiDi、复杂连字**差一个数量级。
CJK 靠 Tiny-TTF 外挂解决得不错，但阿拉伯语/印地语系语言不现实。也没有富文本
编辑。

### 2.5 渲染与性能天花板

- `LV_USE_DRAW_SW = 1`、`LV_USE_DRAW_SDL = 0` — 纯软件光栅化，未启用 GPU；
- `LV_USE_OS = LV_OS_NONE` — 单线程绘制，不利用多核；
- `LV_DPI_DEF 130` 写死 — 无 DPI 自适应、无多显示器缩放。

前两项有改善余地（`LV_USE_DRAW_SDL` 可评估启用），第三项要改的是整个尺寸体系。

### 2.6 跨平台实为零验证

只在 Linux/X11 跑通。锁死平台的**不是 LVGL，是宿主胶水**：

- 热重载用 `sys/inotify.h`（macOS 需 FSEvents/kqueue，Windows 需
  `ReadDirectoryChangesW`）；
- `SIGINT`/`SIGTERM` 是 POSIX 语义；
- Android 还需要独立 Gradle/NDK 轨道 + 应用生命周期（当前
  `while (g_running)` 完全没处理 pause/resume）。

SDL2 本身是真跨平台的，这部分成本可控——但**从未验证过**。

### 2.7 工程化缺位

无 CI、无 formatter、无 linter、无自动回归运行器（`.github/`、`scripts/`、
`tools/` 都被主动删除）。主题的三项一致性检查（hex 正确性、三文件 token 注册
表对齐、变异测试）随 `tools/` 一起消失，**现在没有任何东西能阻止 token 在
`sg_theme.h` / `sg_theme.c` / `theme.md` / `framework.d.ts` 之间静默漂移**。

## 3. 根因：不是 LVGL 做得不好，是设计中心不同

上述每一条都不是 LVGL 的缺陷，而是它的**设计边界**：LVGL 的目标是
"嵌入式单屏 + 触摸 + 资源受限 + 无 OS"。在那个语境下，单窗口、软件渲染、
无线程、无无障碍、简化文本引擎全都是**正确的取舍**。

所以问题不在实现质量，而在于：**把 LVGL 推向桌面，等于逆着它的设计意图，
为每一个桌面语义手工造一层适配。** 已有的三处 SDL 拦截就是这条路的样本，
而完整桌面框架需要的是几十处。

---

## 4. 真正的问题不是技术，是定位冲突

一个必须回答的问题：**stonegui 相对 Qt QML 的独特价值是什么？**

这很尖锐，因为 **Qt QML 本身就是"声明式 UI + JS 引擎 + 属性绑定响应式"**——
和 stonegui 是同构的架构，而它已经覆盖桌面三平台 + Android + 嵌入式
EGLFS，无障碍与原生集成都现成。

只有两个自洽的答案：

**定位 A — 价值是"JSX/React 心智 + 极小体积 + 秒级启动"**
则 LVGL 是**正确**的后端，错的是"完整桌面程序"这个目标。收窄到 HMI /
工控面板 / 一体机 / 嵌入式设备界面，**项目现在就是可交付状态**，后续做的
是打磨而非填坑。

**定位 B — 价值是"一个完整的跨平台桌面应用框架"**
则 stonegui 与 QML/Flutter 做同一件事，却要独自补完它们十几年的积累。
投入产出比不成立，且成品相对现有方案没有优势。**本项目按 B 停止。**

## 5. 后续方案对比

若要重启，按"桌面为主 + 兼顾嵌入式 Linux + 尽量支持 Android"这个目标评估：

| 方案 | 桌面 | 嵌入式 Linux | Android | 无障碍 | 体积/启动 | 可复用 `framework.js` | 评价 |
|---|---|---|---|---|---|---|---|
| **留在 LVGL，收窄定位** | 补丁式 | 强（含无 GPU 裸屏） | SDL2 可行 | 无 | 极小 / 极快 | 全部 | 目标改成 HMI 才成立；**唯一在无 GPU 小设备上不可替代** |
| **自研后端（Skia / wgpu + 自绘控件）** | 需全造 | 需 GPU | 需全造 | 需全造 | 中 | 全部 | 等于重造 Flutter，人年级，除非"造框架"本身就是目的 |
| **Qt / QML** | 成熟 | 强（EGLFS 可无窗口系统直跑） | 成熟 | 有 | 大 / 秒级 | 无（QML 已同构） | **唯一同时命中三个目标**；代价是体量与 LGPL/商业授权合规 |
| **Flutter** | 成熟 | flutter-elinux（社区，非官方） | 最强 | 有 | 大 | 无 | 桌面+Android 很稳，嵌入式是弱项 |
| **Slint** | 好 | 强（可到 MCU 裸机） | 有 | 部分 | 小 | 无（自带 DSL） | 定位与本项目最接近的成品；Rust 生态，授权需评估 |
| **Tauri / WebView** | 好 | 依赖系统 WebView，小设备不可行 | 有 | 继承浏览器（最好） | 中 | 部分（可换 Web 渲染） | 嵌入式直接出局 |

几点补充判断：

- **"嵌入式 Linux 现在都是完整桌面环境"只对一半。** 它是光谱：RK3588 /
  i.MX8 这类 SBC 确实跑 Wayland + GPU，Qt/GTK 体验接近桌面；但无 GPU、
  128 MB 内存的 Buildroot/Yocto 定制 rootfs 上，Qt 要深度裁剪且软渲染很慢，
  GTK 基本不可用。**目标硬件的下限决定了选型**——只到 SBC 级，三个目标就
  塌缩成同一类设备，成熟框架完胜；下探到裸屏级，LVGL 路线才有不可替代性。
- **GTK 因 Android 支持缺失直接出局。**
- 若定位 B 重启，**Qt/QML 与 Slint 是仅有的两个认真选项**。

---

## 6. 结论

1. **停止在 LVGL 上扩展桌面功能面。** 缺口是子系统级的，不是能靠增量改进
   闭合的。
2. **项目不等于失败。** 按定位 A 它已经完成；只是当初挂的是定位 B 的目标牌。
3. **若要交付桌面产品**：转 Qt/QML 或 Slint，不要试图两者兼得。
4. **若目标硬件确实下探到无 GPU 小设备**：LVGL 路线仍有不可替代性，此时
   应把定位改回 A，并按第 2.6 节先做"去 Linux 特化"（把 inotify / 信号处理
   抽成平台接口），那是成本最低、解锁面最大的一步。

## 7. 可迁移的资产

换任何底层，下面这些不会浪费：

- **响应式核心的设计**（[`js/framework.js`](../js/framework.js)，679 行）—— 与
  渲染后端解耦：signal/effect/owner 树、挂载一次 + 属性级更新、`<Show>` /
  `<For>` 作为唯一动态挂载点、`createRoot` 隔离行级 owner 防止级联 dispose。
- **token 化主题的分层**（见 [`theme.md`](theme.md)）—— 语义色阶 + 整数
  token 的二分法、`$token` 活引用、伪状态与 part 的一层嵌套上限，这套模型
  与 LVGL 无关。
- **踩坑记录**——[`roadmap.md`](roadmap.md) 末尾的 History 一节值得重读：
  指针身份判等导致 setter 静默 no-op、`check(true, …)` 式的假测试、
  暗色模式只改一半导致 1.04 对比度。这三类错误与技术栈无关。

真正锁死在 LVGL 上的是 [`lv_bindings.c`](../src/lv_bindings.c) +
[`sg_theme.c`](../src/sg_theme.c) 共 4411 行（约 48%）。

## 8. 如果重来

- **先定"目标硬件下限"，再选底层。** 本项目的所有纠结都源于这一条没先回答。
- **先问"相对现成方案的独特价值"。** 若答案是"更小更快"，就别把目标写成
  "完整桌面框架"；两者互斥。
- **验证跨平台要趁早。** 宿主胶水（文件监听、信号、生命周期）从第一天就
  抽成平台接口，成本几乎为零；积累到 500 行 `main.c` 之后再抽就是重构。
- **别删回归工具。** `tools/` 里那三项主题一致性检查删掉之后，四文件 token
  漂移就再没有任何防线了。
